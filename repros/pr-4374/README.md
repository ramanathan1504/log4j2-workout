# PR #4374 — the Cassandra appender ignored `log4j2.sslVerifyHostName` with `useTls`

https://github.com/apache/logging-log4j2/pull/4374

## Mechanism

With `useTls="true"`, `CassandraManager` called `Cluster.Builder.withSSL()`, which builds `RemoteEndpointAwareJdkSSLOptions` on `SSLContext.getDefault()`. The engine gets the peer host, but no endpoint identification algorithm, so JSSE checks the chain and never the host name. The PR passes a subclass that sets `EndpointIdentificationAlgorithm=HTTPS` when `log4j2.sslVerifyHostName=true`. `Repro.java` runs a TLS server socket in the JVM with a self-signed certificate (trusted through `javax.net.ssl.trustStore`, generated by `keytool` in `run.sh`), points a `Cassandra` appender with `useTls="true"` at `127.0.0.1:<port>`, and counts on the server side the handshakes completed and refused. No Cassandra node is needed: the oracle is the TLS handshake, which happens before any CQL. Each case is a separate JVM.

## Notes

The last row is a residual caveat, not a regression of the PR's purpose: `RemoteEndpointAwareJdkSSLOptions.newSSLEngine` (driver 3.11.5) passes `InetSocketAddress.getHostName()` to `createSSLEngine`, which reverse-resolves an IP literal (the driver's own error shows `localhost/127.0.0.1`). With `host="127.0.0.1"` the certificate is therefore checked against `localhost`, and a certificate carrying only the IP SAN is refused. Users who configure contact points by IP need a certificate naming the reverse-DNS name.
