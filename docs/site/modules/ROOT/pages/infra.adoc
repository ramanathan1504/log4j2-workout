= Backing services
:navtitle: Backing services
:description: The containers the network and NoSQL appenders need, and what each one verifies.

Almost nothing in this bench needs a container. H2, GreenMail, Tomcat 9 and 10,
ActiveMQ Artemis, an in-process JNDI provider and a Spring Cloud Config server
all run *inside the bench JVM*, so every module is exercised by an ordinary
`./bench run` with nothing started first.

Two applications are the exception, because their appenders speak to something
across a socket by definition.

== Starting them

[source,bash]
----
# The network appenders
docker compose -f infra/docker-compose.yml up -d kafka syslog mailhog

# The NoSQL appenders
docker compose -f infra/docker-compose.yml up -d mongodb couchdb cassandra-init
----

[cols="1,1,3"]
|===
| Service | Port | Used by

| `kafka` | 9092 | `Kafka` appender — the topic is consumed to verify
| `syslog` | 5514 | `Syslog` appender, BSD and RFC5424, TCP and UDP
| `mailhog` | 1025 / 8025 | `SMTP` appender — the REST API is queried
| `mongodb` | 27017 | `NoSql` with the `MongoDb` provider
| `couchdb` | 5984 | `NoSql` with the `CouchDb` provider
| `cassandra` | 9042 | `Cassandra` appender
|===

[WARNING]
====
Cassandra takes 60–90 seconds after its container starts before it accepts
connections — far longer than anything else here. A run started too early fails
at appender *construction*, so the appender is absent for the whole run rather
than retrying. `docker compose ps` reports `(healthy)` when it is genuinely
ready.
====

== Two images that no longer exist

`bitnami/kafka:3.9` stopped resolving when Bitnami withdrew its Docker Hub tags
in 2025, and `balabit/syslog-ng:4.8.1` went the same way. The compose file now
uses `apache/kafka:3.9.0` and `balabit/syslog-ng:latest`.

The Kafka switch is not just a name. The Apache image takes `KAFKA_*`
environment variables, which map onto `server.properties` keys; Bitnami took
`KAFKA_CFG_*`. A configuration written for one is *silently ignored* by the
other, and the broker then starts with defaults that do not match the ports you
published.

== What each destination proves

A network appender that cannot reach its destination usually says nothing at
all — UDP has no feedback, TCP appenders retry in the background, and
`ignoreExceptions` defaults to `true`. So the check is always at the far end:

[cols="1,3"]
|===
| Appender | Verified by

| `Socket`, `Http` | Listeners inside the bench JVM, so the exact bytes on the wire can be compared against the layout
| `Syslog` | The receiver's `received.log`, which shows both framings from one run
| `Kafka` | The topic, consumed
| `JeroMQ` | A subscriber attached before publishing — a PUB socket with no peer discards silently
| `SMTP` | MailHog's REST API, the container's own record
| `NoSql`, `Cassandra` | Document and row counts, before and after
|===

== Stopping

[source,bash]
----
docker compose -f infra/docker-compose.yml down
----

Nothing in the bench depends on a container staying up between runs: every app
recreates whatever schema or database it needs.
