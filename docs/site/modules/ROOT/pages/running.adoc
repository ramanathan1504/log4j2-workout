= Running the bench
:navtitle: Running the bench
:description: The bench CLI — running scenarios, sweeping the matrix, and generating a reproduction.

`./bench` is the only entry point. It resolves a real classpath per Log4j
version and forks a JVM, so what executes is exactly what a reproduction zip
would ship — never Maven's own classpath.

== Commands

[source,bash]
----
./bench list                                    # apps, versions, configs, scenarios
./bench run core-java --config xml/filter-all   # one app under one configuration
./bench matrix --scenario exceptions            # that scenario, every Log4j version
./bench coverage                                # what is reached, what is not
./bench repro 4143 --config xml/layout-jsontemplate
----

== Selecting a configuration

Every configuration exists in all four Log4j 2 formats under the same name, so
the format is just a directory:

[source,bash]
----
./bench run core-java --config xml/filter-all
./bench run core-java --config properties/filter-all
----

The extension is inferred from the directory; a bare name means the XML one.
Comma-separate two or more and Log4j merges them, which is how composite
configuration is exercised:

[source,bash]
----
./bench run core-java --config xml/baseline-console,xml/custom-levels
----

[IMPORTANT]
====
One configuration is *not* in all four formats. `arbiters` has no properties
version, because that format has no arbiter support at all and the nearest
spelling throws a fatal `ConfigurationException` rather than degrading. See
xref:configs.adoc[Configurations].
====

== Scenarios

Scenarios are the code side: what the application logs, independent of how it is
configured. `core-java` carries them all.

[cols="1,3"]
|===
| Scenario | Covers

| `messages` | Every `Message` type, lambda and `Supplier` forms, flow tracing
| `lookups` | All 18 built-in lookups, through a live `StrSubstitutor`
| `context` | MDC, NDC, marker hierarchies, propagation across a thread pool
| `exceptions` | Nested causes, suppressed, circular, deep stacks, colliding `equals`
| `rollover` | Drives rollovers, then reports what rolled and what compressed
| `programmatic` | `ConfigurationBuilder` — a whole configuration built in code
| `custom-levels` | `Level.forName`, and the levels the custom-levels configs declare
|===

== Failure detection

The matrix scans for `StatusLogger` errors as well as a non-zero exit, because
checking the exit code alone would mark almost every layout bug as a pass.

One configuration breaks that rule deliberately. `appender-composite` cannot
demonstrate `Failover` without a primary that fails, and a failing appender
reports itself. It emits exactly three errors, all naming `BrokenPrimary`, and
its header says so. Judge that one by whether `logs/composite/failover.log`
filled up.

== Generating a reproduction

[source,bash]
----
./bench repro 4143 \
  --scenario exceptions \
  --config xml/layout-jsontemplate \
  --log4j 2.24.1 --log4j 2.25.4 --log4j 2.27.0-SNAPSHOT
----

Produces `repros/issue-4143/`:

* a standalone Maven project with no parent POM and no reference to this
  workspace, whose dependencies are derived from the configuration it ships —
  so a `JsonTemplateLayout` reproduction pulls in `log4j-layout-template-json`
  rather than silently falling back to the default configuration and
  reproducing nothing
* a filled-in verification matrix, ready to paste into the issue
* the full output of each version's run

The bench itself is never mutated: generation writes only to `repros/`.

== Extra JVM flags

Unrecognised arguments to `./bench run` are passed to the *application*, not to
the JVM, so ad-hoc `-D` flags go through `BENCH_JVM_ARGS`. Mostly this is for
turning the StatusLogger all the way up when an appender fails quietly — which
is how the Cassandra circular-initialisation finding was captured:

[source,bash]
----
BENCH_JVM_ARGS='-Dlog4j2.debug=true -Dlog4j2.StatusLogger.level=TRACE' \
  ./bench run nosql --config xml/appender-nosql
----

Appenders that catch their own exceptions report through the StatusLogger and
leave the exit code at 0, so a run that looks clean at `WARN` can be doing
nothing at all. When a scenario stores or sends less than expected, raise the
level before assuming the configuration is wrong.
