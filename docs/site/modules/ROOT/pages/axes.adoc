= The four axes
:navtitle: The four axes
:description: How the matrix sweeps app, configuration, JDK and Log4j version — and why most cells are skipped.

`matrix` sweeps *application × configuration × JDK × Log4j version*.

[source,bash]
----
./bench matrix                                   # every version, one app/config/JDK
./bench matrix --apps core-java,db --javas 17,21 # widen the axes you care about
./bench matrix --all                             # every valid cell — hours
----

Every axis defaults to a single value except the version one, because the full
cross product is thousands of forked JVMs.

== Most of the cross product is invalid

That is reported rather than run. A cell is skipped, with its reason, when:

[cols="2,3"]
|===
| Condition | Reason given

| The app has no 3.x release path
| `log4j1-bridge has no 3.x release path`

| The JDK is older than the app's class file target
| `core-java is compiled at release 17`

| Log4j 3 with a JDK below 17
| `Log4j 3 requires Java 17+`

| A properties configuration on 3.x
| `properties format removed in 3.x`
|===

A skip is information. A failure you have to explain away is not.

== The JDK axis

Discovered from `/usr/libexec/java_home`, so it reflects what is installed
rather than a list that rots.

Only `java8-baseline` is compiled at release 8. Every other module targets 17
and is skipped on older JDKs rather than failing to load — which is the whole
reason that module exists: without it, the oldest JDK Log4j 2 supports was an
assumption rather than a column.

== The version axis

[cols="1,3"]
|===
| Selector | Log4j

| _(default)_ | `2.27.0-SNAPSHOT` — the local `2.x` build
| `--log4j 2.24.1` | the last line before the `ThrowableStackTraceRenderer` rewrite
| `--log4j 2.25.4` | the line Apache Spark branch-4.2 ships
| `--log4j 2.26.1` / `2.27.0` | current releases
| `--log4j 3.0.0-SNAPSHOT` | the local `main` build
|===

=== Four things about 3.x the bench encodes

. **3.x reads a different system property for the configuration location.** It
  is `log4j.configuration.location`; `log4j.configurationFile` is not read at
  all. Nothing fails when you pass the 2.x name — Log4j quietly uses
  `DefaultConfiguration` — so the run looks fine and tests nothing.
. **3.x pins `log4j-api` to `2.24.3`.** The API is versioned separately; there
  is no `log4j-api:3.0.0-SNAPSHOT`.
. **Modules were split out of `log4j-core`**: `log4j-async-logger`,
  `log4j-compress`, `log4j-csv`, `log4j-script`, `log4j-jdbc`,
  `log4j-jdbc-jndi`, `log4j-conversant`, `log4j-jctools`, `log4j-jndi`,
  `log4j-config-{jackson,properties,yaml}`.
. **Modules that do not exist on 3.x at all**: `log4j-1.2-api`, `log4j-jcl`,
  `log4j-web`, `log4j-jakarta-web`, `log4j-jakarta-jms`, `log4j-jakarta-smtp`,
  `log4j-cassandra`, `log4j-jpa`, `log4j-spring-boot`,
  `log4j-spring-cloud-config-client`.

== Coverage

`./bench coverage` answers two questions that fail differently:

* which Log4j modules are on some application's classpath at all — a gap here
  is a module the bench cannot exercise however it is invoked
* which axis cells have actually been run

The module list comes from the source clone, so it tracks the clone rather than
a list in the repository.
