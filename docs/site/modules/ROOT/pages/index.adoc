= Log4j Bench
:navtitle: Overview
:description: A real-application bench for Apache Log4j, across every module, configuration format, JDK and version line.

A complete, real-application bench for Apache Log4j: every appender, layout,
filter, lookup, message type and configuration format, runnable across the 1.x
bridge, every 2.x line, and 3.x.

It exists for maintainer work. When an issue or a pull request arrives, run it
here against a real application on every affected version, then emit a
standalone reproduction to attach to the issue.

[NOTE]
====
This is not a test suite. Nothing here asserts that Log4j is correct — it makes
Log4j's behaviour *visible* on a given version, JDK and configuration, so that a
change in behaviour is something you can see rather than infer.
====

== The one idea worth reading first

Log4j catches appender exceptions and reports them through `StatusLogger`. The
JVM still exits 0. So *a run that produces no error proves nothing*: a broken
JDBC appender, an SMTP appender that never sends, and a Kafka appender pointed
at a dead broker all look exactly like success from the application's side.

Every app in this bench therefore asserts on an outcome rather than an absence:

[cols="1,3"]
|===
| Application | What it actually checks

| `db`, `jpa`, `jdbc-jndi`
| Rows read back out of the database, counted before and after

| `smtp`
| The message that arrived, and whether the buffered context events are in its body

| `jms`
| The queue, drained, with the JMS message *type* of each entry

| `network`
| What reached each destination — Kafka topic consumed, syslog file grown, MailHog queried

| `custom-plugins`
| That the annotation processor's descriptor exists *and* that the plugins resolve

| `javax-web`, `jakarta-web`
| Which `LoggerContext` a request thread is bound to, and whether `${web:}` resolves
|===

== Scope

[cols="1,1,3"]
|===
| Axis | Size | Notes

| Modules
| 41 of 41
| Every shippable 2.x module is on some application's classpath

| Configuration formats
| 4 + 2
| XML, JSON, YAML, properties, plus both Log4j 1.x formats

| Log4j versions
| 7
| 2.24.1 through 2.26.1, plus the local 2.x and 3.x snapshots. `./bench list --versions`

| JDKs
| 4
| 8, 17, 21, 22 — discovered from `java_home`, not hard-coded
|===

`./bench coverage` recomputes module reach from the source clone and the
resolved classpaths, so the number above does not go stale as either moves.

== What it helps you do

Two jobs, written up end to end in xref:workflows.adoc[Workflows]:

[cols="1,3"]
|===
| Job | The loop

| *Review a pull request*
| Read the diff, work out which app reaches the module it changes, build the
branch into your local repository so `./bench` can select it, baseline against a
release, run it, sweep for what it broke elsewhere, attach a verification matrix

| *Reproduce and fix an issue*
| Read the report, run the version it names, find the first version that fails
and the last that passes, emit a standalone reproduction, fix it upstream, then
prove both halves — what failed now passes, and what passed still does
|===

Both stay in the terminal from beginning to end. `./bench issue` and
`./bench pr` read GitHub, `./bench run` and `./bench matrix` run it, and
`./bench repro` produces the thing you attach.
