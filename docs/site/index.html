Log4j Bench

A real-application bench for Apache Log4j — every module, configuration format, JDK and version line, verified by what actually happened rather than by the absence of errors.

The one idea worth reading first. Log4j catches appender exceptions and reports them through StatusLogger. The JVM still exits 0. So a run that produces no error proves nothing — a broken JDBC appender, an SMTP appender that never sends, and a Kafka appender pointed at a dead broker all look exactly like success from the application's side.

Every application here therefore asserts on an outcome: rows read back, mail consumed, a queue drained, a topic polled.

Running it

./bench is the only entry point. It resolves a real classpath per Log4j version and forks a JVM, so what executes is exactly what a reproduction zip would ship — never Maven's own classpath.

./bench list                                    # apps, versions, configs, scenarios
./bench run core-java --config xml/filter-all   # one app under one configuration
./bench matrix --scenario exceptions            # that scenario, every Log4j version
./bench coverage                                # what is reached, what is not
./bench repro 4143 --config xml/layout-jsontemplate

Every configuration exists in all four Log4j 2 formats under the same name, so the format is just a directory. Comma-separate two and Log4j merges them, which is how composite configuration is exercised:

./bench run core-java --config yaml/filter-all
./bench run core-java --config xml/baseline-console,xml/custom-levels

The four axes

matrix sweeps application × configuration × JDK × Log4j version. Every axis defaults to a single value except the version one, because the full cross product is thousands of forked JVMs.

Most of that cross product is invalid, and that is reported rather than run. A skip is information; a failure you have to explain away is not.

The JDK axis is discovered from java_home, so it reflects what is installed. Only java8-baseline is compiled at release 8 — without it, the oldest JDK Log4j 2 supports was an assumption rather than a column.

Configurations

The mirrors are not mechanical translations. Where a format genuinely cannot express what the XML does, the file says so and takes the nearest honest route.

LimitationDetail
arbiters has no properties versionThat format has no arbiter support at all; the nearest spelling throws a fatal ConfigurationException.
Composite filters in propertiescreateFilter always passes onMatch/onMismatch, which CompositeFilter does not declare.
JSON carries no commentsLog4j 2 allows them; Log4j 3 fails with an NPE rather than a parse error.

$ versus $$ is the other thing worth internalising: $ resolves once while the configuration is built, $$ defers to each event. Use $ where $$ was meant and every event silently gets the value the first one had.

Findings

Everything below was found by building the bench, and every entry was checked against the source clone rather than against documentation. These are observations about behaviour, not bug reports — several are documented behaviour that merely fails confusingly; a few look like genuine defects. Which is which is a maintainer's call.

Failures that kill the application

Each escapes configuration and reaches LogManager.getLogger, so the application dies with ExceptionInInitializerError in whichever class holds the first static logger.

  • fatal Arbiters in the properties format. No arbiter support exists; the nearest spelling throws No name attribute provided for Appender.
  • fatal A nested custom level in properties. It is customLevel.<NAME> = <int> — the key is the name. The nested spelling makes the builder parse the name as an integer.
  • fatal // comments in JSON on Log4j 3. Log4j 2 enables ALLOW_COMMENTS; Log4j 3 leaves root null and NPEs at the first logger call.

Failures that are completely silent

  • silent Log4j 3 reads log4j.configuration.location, not log4j.configurationFile. Passing the 2.x name does not fail — Log4j quietly uses DefaultConfiguration, so an entire 3.x column can pass while testing nothing.
  • silent JeroMQ endpoints are <Property name="endpoint"> elements, not attributes. As attributes the appender still builds, binds nothing, and publishes into the void.
  • silent SortByModificationTime's attribute is recentFirst, not ascending. The wrong name is rejected while the sorter builds with its default, so retention order silently stays whatever that is.

Where the error names the wrong thing

  • log4j-jpa cannot initialise on any JDK 16+ without --add-opens java.base/java.lang=ALL-UNNAMED. Its ThrowableAttributeConverter reflects into Throwable.cause in a static initialiser and catches only NoSuchFieldException. The provider then reports a deployment failure from its own Class.forName, naming neither Log4j, nor the converter, nor the flag.
  • The JNDI DataSource source resolves its name while the appender is being built, so the binding must exist before the first logger acquired anywhere in the JVM. A conventional private static final Logger initialises at class load — so binding in main() is already too late.
  • InitialContext copies only java.naming.* from system properties, so a provider needing its own keys cannot be configured with -D at all. It falls back to its defaults and fails with a message that says nothing about where it tried to connect.

Interactions between modules

  • log4j-appserver and log4j-web together defeat the per-webapp LoggerContext. appserver routes the container's logging into Log4j, so Tomcat logs before any webapp initialises, creating a context on the parent classloader. log4j-web's SCI then hits ClassLoaderContextSelector's parent-walk, which returns that context without applying the ServletContext entry.
  • log4j-jakarta-smtp contains no appender. SmtpAppender lives in log4j-core and picks its implementation by ServiceLoader, so the jar silently replaces the whole mail stack with nothing naming which won.
  • Log4j2EventListener's @ConditionalOnProperty has no effect. It is registered in spring.factories as an ApplicationListener, and those are instantiated without bean definitions — conditions are a bean-definition mechanism.

Layouts that cannot do what they look like they can

  • CsvParameterLayout throws NPE on any event with no parameters. getParameters() is null for SimpleMessage, and toSerializable hands that to CSVFormat.printRecord. One per event, no recovery.
  • MessageLayout.toByteArray() is return null; — it works with JMS and fails on every event with any stream appender.
  • Rfc5424Layout's mdcId must not contain @, even though name@enterprise is what appears on the wire. Log4j appends the number itself.

Ordering and lifecycle

  • Delete's sibling conditions are order-sensitive, because IfAccumulatedFileCount is stateful. A counter ahead of the glob also counts the active file. The properties format cannot express sibling order at all, so nesting is the only portable formulation.
  • RollingFileManager uses non-daemon threads, started on the first compressing rollover. The JVM cannot begin shutting down, and the hook that would stop Log4j only runs once shutdown has begun — so a short-lived app hangs on exit unless it calls LogManager.shutdown().
  • Under log4j-to-jul, ThreadContext is a no-op. JULProvider registers NoOpThreadContextMap, so code reading back its own trace id gets null.

Environment compatibility

  • log4j-cassandra is built on DataStax driver 3.11, which negotiates native protocol v4 at most and cannot read Cassandra 5's schema tables. The connection never completes rather than failing, so the appender hangs at construction with no error.
  • log4j-couchdb cannot work with modern Gson. LightCouch 0.2.0 calls registerTypeAdapter(JsonObject.class, …), which Gson 2.11 forbids, so the provider cannot be constructed — and the message names neither Gson's version nor log4j-couchdb.
  • EclipseLink 2.7 cannot drive H2 2.x. Its DDL emits H2 1.x syntax and it treats the failure as a warning, so deployment reports success and every insert fails with "table not found".
